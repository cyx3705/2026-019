# 模块开发手册

面向为 HistoryVulcan 开发模块的人和 AI。Diana 把工作树、门禁提交、调用型试用和并回主线暴露成
MCP 工具。测试运行包用 `diana.trial.load`（直接调 Vulcan 热重载）；日常收尾只有两条命令：`diana.release.cycle`
和（若要合并）`diana.worktree.merge`。cycle 与 merge 对模块也只调同一热重载接口，无需记发布脚本路径，也不需要为了看一眼候选模块而把它
`publish=true` 到正式 Clio 槽，更不要改发现根或拷 AppData。

**工作区边界：AI 长期只在 Diana 管理的 `F:\ai工作区` 工作。** Janus、Mercury、Minerva 等模块仓库
主线是源码基线、合并目标和正式发布来源，不是 AI 的日常编辑目录。AI 不应直接进入这些主线目录修改；
由 `diana.worktree.create` 从主线拉出分支，所有真实改动、提交和候选验证都发生在 F 盘工作区。
要并回时用 `diana.worktree.merge`。修改 Diana 自身主线是唯一例外。

本手册只负责**流程**：从开工作区到正式发布，每一步用哪条命令、卡住时看哪里。
**接口事实不在这里**——宿主能注册什么窗口、命令怎么命名、MCP 如何暴露，由 HistoryVulcan
自己的文档作数，读法见下一节。

## 先学会查文档

跨项目读文档只有一条路：**先 `diana.docs.catalog` 拿到通道索引，再调用其中一条通道**。
不要去打开别的项目的 worktree，也不要依赖手写的文件表——两者都会过期。
Cursor 会话里的 MCP 工具表也会过期：现场以 `diana.relay.list` 为准，表里没有的工具用
`diana.relay.call` / `describe`，不要猜脚本路径。

```
diana.docs.catalog                       # 列出全部通道与各自的文件名，把输出留在对话里
diana.docs.vulcan                        # 只列出宿主通道里有哪些已发布文档
diana.docs.vulcan file=docs/HistoryVulcan_消费变更摘要.md heading=4.0.0
```

`file` 可以抄 catalog 的完整相对路径，也可以只写通道内唯一的文件名。
API 手册和消费变更摘要都超过 12 KiB：**必须加 `heading=` 读一节**，否则通道只返回章节目录。
消费变更摘要用 **版本号**（当前迁移可用 `heading=4.0.0`），不要用 `heading=主要变化`——那一节含全部历史版本。
不要把整份说明书灌进对话。

各模块的消费文档同理（`diana.docs.janus`、`diana.docs.mercury`、`diana.docs.minerva`、
`diana.docs.diana`……通道名以 catalog 的输出为准）。读到的是各项目版本化候选 `z-Publish/HistoryX-vX.Y.Z/docs/`
里的已发布 Markdown；目录不存在时明确报错，不回退旧发布目录，也不读取源码树草稿。

开发模块时最常查的几份：

| 想知道 | 去哪查 |
|---|---|
| 宿主提供哪些 API、指令怎么写 | `diana.docs.vulcan file=docs/HistoryVulcan_API与指令手册.md heading=…` |
| 能注册什么窗口、页面怎么嵌 | `diana.docs.vulcan file=docs/HistoryVulcan_UI风格与嵌入页面规范.md` |
| 运行时有哪些已知限制 | `diana.docs.vulcan file=docs/HistoryVulcan_运行时约束与已知限制.md` |
| 宿主升级后消费侧要改什么 | `diana.docs.vulcan file=docs/HistoryVulcan_消费变更摘要.md heading=4.0.0` |
| 别的模块对外暴露了什么 | `diana.docs.<该模块通道>` |
| 本手册自身 | `diana.docs.diana file=模块开发手册.md` |

### Cursor 连不上宿主 MCP

手册里的 `diana.*` 都从宿主 MCP 来。Cursor 用户配置是 `%USERPROFILE%\.cursor\mcp.json` 里的
`history-vulcan`，`url` 必须是当前宿主的 `http://127.0.0.1:<mcp.port>/mcp`（以
`vulcan.mcp.status` 为准，不要抄死旧端口）。

`mcp.token` **一旦写入后台设置**，网关对回环也要 Bearer（MS-02）。配置里只有 URL、没有头时，
Cursor 会报 live tool discovery 失败，宿主日志是：

```
[Warn] [mcp] 拒绝一次请求: Authorization 缺失或 token 不匹配(MS-02)
```

同一条目补上令牌（从 `%AppData%\HistoryVulcan\service\settings.json` 的 `mcp.token` 取；
`vulcan.app.get key=mcp.token` 只显示「已配置」，不会回显原文）：

```json
{
  "mcpServers": {
    "history-vulcan": {
      "url": "http://127.0.0.1:<mcp.port>/mcp",
      "headers": {
        "Authorization": "Bearer <mcp.token>"
      }
    }
  }
}
```

令牌未设置时保持「本机回环可信」，不必加头。带令牌的 `mcp.json` **不要提交进任何仓库**。
改完后必须在 Cursor MCP 面板把该服务器关掉再打开，会话工具表才会重建。

## 全流程

```
diana.docs.catalog + diana.docs.vulcan   先读正式宿主合同
        ↓
diana.worktree.create   开一个 AI 工作区（新分支，不碰主树）
        ↓
【grok 专属】把对话根搬进该工作区（先让开主树 main，再切根，再切回功能分支）
其他 AI 跳过本步：对话留在当前根，按工作区绝对路径改文件
        ↓
       改代码
        ↓
diana.trial.load path=<工作区候选或历史包目录>
        直接调 Vulcan 热重载（vulcan.module.install）
        ↓
diana.release.cycle name=<模块> msg=<说明> worktree=<工作区>
        门禁 + 写入版本化候选 + 提交 + 同一热重载接口
        ↓
   继续在此工作区开发（再 cycle）
        或
【grok 专属，且仅当对话根已在工作区内】先把对话根迁出工作区（项目主树或 Diana）
        ↓
diana.worktree.merge project=<项目> name=<工作区>
        并回 main、安装主线候选、回收工作区（分支保留）
```

主树 `publish=true` 只用于正式 Clio z（例如 Diana 在自己主线上 cycle）。不要把工作区路径传给
`publish=true`。

## 一、开工作区

```
diana.worktree.create project=2026-021-HistoryMercury slug=explorer-notify agent=claude
```

得到 `F:\ai工作区\<项目>\<短SHA>-<序号>-<标识>`，分支 `ai/<项目>/<同名>`。

同时会在工作区里生成 `Directory.Build.user.props`，把 `HistoryVulcanPackageRoot` 指回来源库根。
各工程按相对路径引用宿主快照，而工作树落在库根之外，少了这个覆盖点会报上百个「找不到类型」。
该文件不入库（各项目 `.gitignore` 已登记），所以工作区从诞生起就是干净的。

- **不要在模块主树上改**。主树是发布和对照的基准；工作区是 AI 的唯一日常编辑面，分支提交可再生但
  主树提交是正式发布来源。
- 位置不硬编码：`diana.worktree.root path=...` 改默认，或单次传 `root=`。默认 `F:\ai工作区`。
- 目录名是 `<短SHA>-<序号>-<开的AI>-<要解决的问题>`，`agent=` 必填：工作区留在盘上的时间
  远长于开它的那轮对话，没有来源和意图就没人敢动它。
- **开销要克制**。项目里已经有一个"开了没干活"的工作区（无提交、无改动）时，默认拒绝再开一个——
  那多半是上一轮对话的残留，接着用或先回收即可；确实要并行才传 `confirm=true`。
  对话窗口随时废弃，工作区不会跟着消失。
- `diana.worktree.list` 会逐个报「干净 / 有改动」，收尾前扫一眼别漏下未提交的东西。
- **切根是 grok 专属。** Cursor 的 `move_agent_to_root` 目前只有 grok 能用。其他 AI 不要尝试迁对话根，也不要把「没切根」当成流程失败：对话留在当前根（通常是 Diana 主树），按 `create` 返回的绝对路径改 F 盘工作区。grok 仍按下面四步把对话根搬进工作区。

### 搬进工作区（grok 专属）：先切目录，再切分支

其他 AI 不要执行本节。开完工作区不等于对话已经在里面。**grok 必须把对话根搬进这个工作区**——这是故意要做的，必须忍受。
Cursor 把对话根迁到目标目录时，会在目标里执行 `git checkout main`。Git 规定**同一条分支同一时刻
只能被一个 worktree 占用**；模块主树已经占着 `main`，于是迁根直接失败：

```
fatal: 'main' is already used by worktree at C:/OneHistory/HistoryClio/<模块主树>
```

这不是脏工作区，提交再干净也过不去。也不是「不该迁根」或「Git 不允许开工作区」——工作区本来
就该停在 `ai/<项目>/<工作区名>` 上，主树才该占 `main`。迁根工具会去抢 `main`，所以用下面四步
把它让开，而不是放弃迁根。

**不要**为了躲开这条报错而不搬对话根。**不要**在工作区里先 `checkout main` 来「配合」迁根。
**不要**把对话留在模块主树再改（那是日常编辑主线，违规）。**不要**把主树长期停在 detached HEAD。

规定顺序是**先让开主树的 main，把对话根落到工作区目录，再把工作区切回功能分支，最后把主树 main 复原**：

```
# 1. 主树临时让开 main（两边若还在同一 SHA，工作区文件不会变）
git -C C:\OneHistory\HistoryClio\<模块主树> checkout --detach

# 2. 把对话根迁到 F:\ai工作区\<项目>\<工作区名>
#    （仅 grok：move_agent_to_root。其他 AI 没有这条工具，不要改走打开文件夹凑合）

# 3. 工作区切回功能分支（迁根工具可能已经把它切到 main，必须切回来）
git -C F:\ai工作区\<项目>\<工作区名> checkout ai/<项目>/<工作区名>

# 4. 主树立刻回到 main
git -C C:\OneHistory\HistoryClio\<模块主树> checkout main
```

四步做完应是：对话根在 F 盘工作区、该树在 `ai/...` 分支、主树仍在 `main`。任何一步失败都先把主树
`checkout main` 复原，不要留下 detached 主树。

**唯一的例外是 Diana 自己。** Diana 是造工作区的工具，没法用自己造的工作区改自己，
所以改 Diana 必须动本仓库主树——这是特例，不要推广到其他模块。

## 二、改代码

模块对宿主的依赖面是**已发布的 z 快照**，不是宿主源码树。

这不是洁癖，是踩过的坑：Mercury 4.5.1 的 csproj 写的是「只要宿主源码树存在就引用源码工程」，
于是宿主工作区一有未发布的在途改动，模块就链接到根本没在运行的宿主二进制，
装载时在 WPF 视图构造处抛 `XamlParseException: 设置 connectionId 时引发了异常`，
宿主只记一行 Warn 继续走，**桌面坞从桌面上无声消失**。

所以新模块的 csproj 应当：

- 默认 `HintPath` 引用 Vulcan 4.0.0 的平铺宿主快照 `z-Publish/host/HistoryVulcan.*.dll`，`<Private>false</Private>`；
- 要对宿主源码联调时**显式**传 `-p:HistoryVulcanSourceAvailable=true`，不做自动切换；
- 加一个前置校验目标，两条路径各自检查前提缺失时直接报错，而不是报成一堆「找不到类型」。

普通模块自己的候选仍使用版本化目录 `z-Publish/HistoryX-vX.Y.Z/`；只有宿主当前快照使用
`z-Publish/host/` 平铺形状，旧宿主包只能从 `z-Publish/history/` 取用。模块构建前先确认平铺
`manifest.json` 的 `product=HistoryVulcan`、版本和 `SHA256SUMS` 与 `host/HistoryVulcan.exe` 存在。
`HistoryAurora` 是独立应用，当前构建脚本尚未接受统一 `-OutputRoot`，因此不在 Diana 模块登记表；
不要为它临时添加模块适配器，先刷新 Vulcan 宿主，再按 Aurora 自己的门禁验证。

可用 `b-Code-Samples/` 下的 DemoModule 作为起点（`ModuleInfo`、命令类、`.panel.json`）。

另一条同源的坑：**测试工程不会从模块工程传递 `HintPath` 引用**。模块侧从
`ProjectReference` 改成 `Reference` 之后，Smoke 必须自己声明需要的宿主程序集。

## 三、一轮：门禁、写入工作区 z、提交、试用

```text
diana.release.cycle name=HistoryMercury msg=说明 worktree=<工作区名或绝对路径>
```

`worktree=` 可传 `diana.worktree.create` 返回的绝对路径，也可传该项目在 AI 工作区根下的目录名。
这条命令会等待管线结束（不再立刻返回 run 就不管）：构建、合同、Smoke，然后把已验证候选写入
**该工作树自己的** `z-Publish/HistoryX-vX.Y.Z`，再 `git add`/`commit`。
提交成功后调用 `vulcan.module.install` 热重载运行区同名模块。测试失败不回滚提交，也不自动恢复；
需要恢复时手动选择主树候选或 `z-Publish/history/HistoryX-vX.Y.Z` 再热重载。

省略 `worktree` 时走主树：`publish=true` 写入正式 Clio z、热重载，再提交。HistoryDiana 只允许这条
主线 cycle，不要给它传 worktree。

`status` / `log` 只读，给超时或自发布热重载后看日志，不要当成启动入口。
`worktree` 与正式促级互斥，cycle 已按有没有 `worktree=` 选好路径。

门禁包括：候选构建、Diana 强制对齐的模块合同、以及登记表里为该模块配置的验证（通常是 Smoke）。
**门禁拦下来时，优先改代码，不要改门禁的期望值**——除非那个期望本身描述的就是过时的事实
（例如新增了一个命令类、模块版本号变了）。这类修正要在提交信息里说明为什么。

## 四、测试与部署都走 Vulcan 热重载

未提交、不想跑完整门禁时，先构建出完整候选包，再用一条命令热重载运行包：

```
diana.trial.load path=<z-Publish/HistoryX-vX.Y.Z>
```

`path` 必须是含 manifest、程序集和完整 `SHA256SUMS` 的包根，可以选择当前候选，也可以选择
`z-Publish/history/HistoryX-vX.Y.Z` 中的历史包。`diana.trial.load`、`diana.release.cycle`
和 `diana.worktree.merge` 对模块都只调用 `vulcan.module.install`，与 Vulcan 模块页「热重载」按钮相同：
在运行区外校验与 staging，卸载同名模块，原子替换 `%AppData%\HistoryVulcan\Modules/<模块名>`，
再只扫描该运行区注册命令与 UI。

候选不会进私有内存，也不会与正常模块并存。`trial.list/call/unload`、`ui=true` 和
`vulcan.module.trialui.*` 已退役。测试不通过时，人工再次选择主树候选或历史包热重载；系统不自动恢复。

## 五、并回主线

工作区干净且 `cycle` 已提交后，若本轮要结束：若对话根已经在工作区内（grok 切过根），先把**对话根迁出工作区**（迁到该项目主树或 Diana）。其他 AI 对话本来就不在工作区里，直接 merge：

```text
diana.worktree.merge project=2026-021-HistoryMercury name=<工作区目录名>
```

合并会删除工作区目录。对话根还留在里面时，之后的迁根会在已删除路径上跑 git，直接失败。
迁到别的仓库后立刻 `git branch --show-current`：迁根工具可能在目标仓建出源工作区的 `ai/...`
分支，这时 `checkout main` 并删掉误建分支，不要在别人的分支名下改这个仓库。

**Grok / Cursor：删工作区必须先切回 Diana。** Cursor 能把对话根钉在某个 worktree 上，钉住的
目录就被独占，`Permission denied` 删不掉。只迁到模块主树不够——Cursor 内部仍可能以已卸掉的
工作区路径为当前根。规定顺序：

```
# 1. merge 前先把对话根迁出工作区（见上）
diana.worktree.merge project=<项目> name=<工作区目录名>

# 2. 目录仍在：把对话根迁到 Diana 主树（不要停在模块主树）
#    move_agent_to_root → C:\OneHistory\HistoryClio\2026-019-HistoryDiana
git -C C:\OneHistory\HistoryClio\2026-019-HistoryDiana checkout main
# 若出现源工作区的 ai/... 分支，删掉误建分支

# 3. 再删 F:\ai工作区\<项目>\<工作区名>
```

其他 AI 对话本来就不在工作区里，merge 即可。

主树必须在 `main`。优先快进，不能快进则 `--no-edit` 合并。合并后从主线解析唯一版本化候选，
调用 `vulcan.module.install` 热重载运行包，再删除工作区目录。

主树 z 来自合并过来的工作区候选 z，不是从工作树再跑一次 `publish=true`。
`publish=true` 仍只允许主树（Diana 发布自己，或以后要在主线上正式促级）。

Diana 不提供 push 或建 PR。

促级前必须对齐三处身份，否则管线直接拒绝：

| 位置 | 内容 |
|---|---|
| 版本源 | csproj 的 `Version` 或 `<模块>Version.props` |
| 源清单 | `b-Code-*/module.manifest.json` |
| 快照清单 | `z-<模块>/module.manifest.json`（由管线写入） |

新模块要能被管线发布，需在 `2026-019-HistoryDiana/b-Code/module-publish.manifest.json`
登记一项，并提供构建脚本。可直接照抄任一现有模块的构建脚本逐词替换——
事务结构（stage/backup/failed + 校验和清单）必须保持一致。
`diana.release.modules` 可查当前已登记的模块。

## 六、先部署后提交

**顺序是先部署、后提交，不能反过来。** `diana.release.cycle` 已经按这个顺序做完：
门禁和写 z 成功之后才 commit。不要先手工提交再 cycle。

候选重载失败不回滚已经成功的提交。继续改代码后再 cycle，或手动选择主树候选/历史包恢复。

工作区改动并回主干用 `diana.worktree.merge`；不要先手工 merge 再删工作区。
闲置、与 main 齐平的工作区也用 `merge` 回收。分支一律保留。Diana 不 push、不建 PR。

## 七、宿主开发（与模块的差别）

HistoryVulcan 用**同一套** `worktree.create` / `release.cycle` / `worktree.merge`，不要另找脚本。
差别来自它是正在运行的 EXE，不是可回收模块：

```
diana.docs.catalog + diana.docs.vulcan
        ↓
diana.worktree.create project=2026-023-HistoryVulcan slug=<问题> agent=<ai>
        ↓
改工作区里的宿主源码（不要改 Clio 主树）
        ↓
diana.release.cycle name=HistoryVulcan msg=<说明> worktree=<工作区>
        门禁 + 写入该树 z-Publish/host（旧快照归档到 history/）+ 提交
        **不** trial.load（宿主不是模块）
        ↓
diana.worktree.merge project=2026-023-HistoryVulcan name=<工作区>
        并回 main、回收工作区。**不**用 module.reload 替换 EXE。
正式 EXE 若仍在跑，merge 会直接失败——Diana 住在该进程里，不能自己停自己。
        先停正式 `HistoryVulcan.exe`，再 merge，再启动新 EXE（后台加 `--service`）。
```

Vulcan 4.0.0 的宿主刷新必须先于任何依赖宿主快照的应用或模块验收；因此 Aurora 若要单独验收，
顺序是“刷新 `z-Publish/host` → 运行 Aurora 自己的构建/质量门禁”。在 Aurora 的入口和快照契约
与 Diana 统一前，不登记 `HistoryAurora`，也不把它写入普通模块发布清单。

这是接受的约束，不是要修掉的缺陷：MCP 依赖宿主进程，宿主侧开发保持克制，不为合并做自动停进程。
不要 `diana.trial.load` 宿主快照，不要改 `vulcan.module.roots` 去“装”一个新宿主。
`diana.release.modules` 会列出 `HistoryVulcan  host  2026-023-HistoryVulcan`。

宿主 cycle 时，若版本升了但 `PublicAPI.Unshipped.txt` 与上一版相同，发布器会把
`eng/public-api-baselines/<旧版>` 复制为新版本目录，不必手拷。API 真变了则门禁失败，
审阅后再建新基线，不会自动批准新合同。

替换正式 `HistoryVulcan.exe` 才需要停进程（DEC-006）。模块热重载仍不关宿主。

## 卡住时看哪里

| 现象 | 先看什么 |
|---|---|
| `release.status` 一直「仍在运行」 | `release.log` 看末尾；管线子进程可能已死在某一步 |
| 重载后模块未出现 | 包 manifest/SHA 是否完整，程序集身份是否与目录名一致；查看 Vulcan 模块日志 |
| 门禁报「模块版本 expected≠actual」 | 三处身份没对齐 |
| 促级后宿主没换新 | 看管线末尾是否成功热重载；未运行时下次启动才装载 |
| 桌面上的 UI 消失但命令还在 | 宿主日志搜「创建 UI 模块 ... 失败」，多半是建界面时抛异常 |
| 测试候选不通过 | 手动选择主树候选或 `z-Publish/history/HistoryX-vX.Y.Z` 再次重载；不会自动恢复 |
| 合并后工作区删不掉 / DLL 被占用 | 确认安装操作已结束；工作区包不是运行槽，Vulcan 运行副本应只在 AppData |
| merge 后工作区 Permission denied | **仅 grok。** Cursor 独占该路径。先 `move_agent_to_root` 到 **Diana 主树**，`checkout main` 清掉误建 `ai/...`，再删 F 盘残留。只迁到模块主树不够 |
| 迁根报 leftover 不是 git 仓库 | **仅 grok。** merge 已卸工作区 `.git`，Cursor 仍钉在该路径上做 `checkout --detach`。先迁到 Diana 放开占用；若迁根工具还在残留目录跑 git，给该目录一个可 detach 的 HEAD 再迁 |
| 想看候选却去改 roots / 手工拷 AppData | 改用 `diana.trial.load path=<完整包目录>` 或模块页「热重载」 |
| `trial.load` 报这是宿主 | 对。HistoryVulcan 走 cycle/merge，不要试用装载 |
| `relay.list` 报 InvalidOperationException | 旧 Diana 在读 OneHistoryStudio。需要 HistoryDiana 1.10.10+，连当前宿主 `mcp.port` |
| Cursor 报 MCP live tool discovery 失败；日志 `Authorization 缺失或 token 不匹配(MS-02)` | `mcp.token` 已设置，Cursor `mcp.json` 缺 Bearer。按「先学会查文档」里 Cursor 连不上宿主 MCP 补 `headers.Authorization`，再开关该服务器。不要把令牌写入仓库 |
| Cursor 工具表没有 cycle / merge，却还有 start / remove | 会话表过期。`diana.relay.list` 看现场；用 `diana.relay.call` 调 cycle/merge |
| cycle 报「找不到运行记录」 | 1.10.11 起应消失。若仍出现，立刻 `diana.release.status`：管线可能其实在跑 |
| 文档通道把整本手册灌进对话 | 长文加 `heading=章节标题或版本号`；超过 12 KiB 不带 heading 只返回目录。消费变更摘要用 `heading=4.0.0`，不要用 `heading=主要变化` |
| 切根报 `main is already used by worktree` | **仅 grok。** 迁根工具会抢 `main`，按第一节四步：主树 detach → 迁根 → 工作区切回 `ai/...` → 主树 `checkout main`。其他 AI 不要切根 |
| merge 后迁根报 ENOENT / spawn git 失败 | **仅 grok。** 合并已删工作区。应在 merge **之前**把对话根迁走 |
| 迁根后当前分支是其他项目的 `ai/...` | **仅 grok。** 迁根工具把源分支名建到了目标仓。立刻 `checkout main`，删掉误建分支 |
| 宿主 merge 报正式 EXE 仍在运行 | 先停正式 `HistoryVulcan.exe`，再 merge，再启动。MCP 住在该进程里，不会自动停宿主 |

## 相关命令一览

| 命令 | 用途 |
|---|---|
| `diana.worktree.root/create/list/merge` | AI 工作区；merge 并回 main 并回收 |
| `diana.release.modules/status/log/cycle` | cycle 跑完并提交；status/log 只读排障 |
| `diana.trial.load` | 把候选或历史包交给 Vulcan 热重载（与 cycle/merge 同一接口） |
| `diana.docs.catalog` / `diana.docs.<通道>` | 跨项目已发布说明书；查宿主接口和别的模块都走这里 |

## MCP 暴露边界

Diana 模块声明 `mcpExposure: standard`。当前固定登记 24 条命令，另按现场版本化候选动态登记文档通道；
点号命令投影为下划线工具名，例如
`diana.trial.load` → `diana_trial_load`。

| MCP 等级 | 命令 |
|---|---|
| `readonly` | `docs`、`kit`、`project` 全部；`relay.list/describe`；`release.modules/status/log`；`worktree.list` |
| `standard` | `relay.call`；`release.cycle`；`trial.load`；`worktree.root/create/merge` |

`worktree.root` 省略参数时虽然只是查询，但同一描述符也能写设置，因此整体按 `standard` 暴露。
`trial.load` 只通过受信任的宿主来源调用安装接口；普通远程 MCP 不能直接获得任意 DLL 安装能力。
`relay.call` 只能调用当前 MCP 策略已经可见的工具，不能越过宿主策略访问 hidden/dangerous 工具。
