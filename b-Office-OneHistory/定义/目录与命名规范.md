# OneHistory 目录与命名规范

跨项目一致的命名与结构约定。名词定义见 [`OneHistory总览.md`](./OneHistory总览.md)。

## 指令命名

合法形态恰有两种，全小写、无连字符、不留别名（HistoryVulcan DEC-025）：

| 形态 | 含义 | 类 |
| --- | --- | --- |
| `<域>.<类>.<方法>` | 业务指令的默认形态 | 第二段 |
| `<域>.<方法>` | 该域的**无类直接方法**，为快捷方法保留 | 无类 |

类推导是纯结构判定，不做语义猜测：段数 ≥ 3 取第二段；段数 = 2 判为无类；
描述符显式声明的 `CommandClass` 优先。两段名的首段是**域**，不是类。

现有域：`vulcan`（宿主内置）、`janus`、`mercury`、`minerva`、`diana`、
域清单的权威源是运行期注册表
（`CommandRegistry.Domains()`），任何代码都不得硬编码域名字面量。

### 域聚焦

控制台可聚焦到某个域，之后只输入 `类.方法`。聚焦期间输入首段若命中**已注册域**
则按绝对名解析，因此 `vulcan.*`、`mercury.go` 在任何聚焦状态下都能直接输入。
**任何域都不需要提供"退出聚焦"指令**。

## 版本与身份

每个项目**恰有一个**版本源，其余位置一律从它派生：

| 项目 | 版本源 |
| --- | --- |
| HistoryVulcan | `b-Code-HistoryVulcan/VulcanVersion.props` |
| HistoryJanus | `b-Code-Studio/JanusVersion.props` |
| HistoryDiana | `b-Code-HistoryDiana/HistoryDianaVersion.props` |
| HistoryMercury | `b-Code-MercuryDock/HistoryMercury.csproj` 的 `<Version>` |
| HistoryMinerva | `b-Code-HistoryMinerva/build/HistoryMinerva.Version.props` |

跨项目依赖的版本（例如 Janus 依赖的宿主版本）同样只写一处：
Janus 用 `JanusVersion.props` 的 `RequiredHistoryVulcanVersion`，发布脚本与质量门禁都从那里读。

**反面教材，不要重蹈**：

- 宿主契约版本曾以字面量硬编码在 2 个脚本 + 1 个用例共 6 处。
- Mercury 版本曾存在 3 处（csproj / manifest / `ModuleInfo.cs`），漏改一处导致
  整个模块静默不装载，界面上表现为活动坞和命令集页一起消失。
- 测试里用硬编码版本断言，正好掩盖了上面那次漏改。
  **断言要比对两个真实来源，不要比对字面量。**

## 文档结构

每个项目的 `b-Office`（Diana 因托管公共区而拆成 `b-Office-Diana`）：

| 目录 | 内容 | AI 默认是否读 |
| --- | --- | --- |
| `current/` | 现行合同：项目概览、技术合同、有效决策、验证合同 | 是 |
| `package/` | 对外消费文档，供别的项目和 AI 稳定引用 | 按需 |
| `history/` | 已失效的版本方案，只作追溯 | 否 |

`current/` 四份是现行事实的唯一权威。技术合同必须声明当前开发版本，
否则质量门禁会红——**这不是形式主义，Janus 的技术合同曾因此停在 3.3.0 落后三个版本。**

## 生产源码里不写版本叙事

生产代码（各项目的 `b-Code*`）里不得出现 `V3.2.1`、`DEC-008`、`移植自`、
`今后每个版本` 这类历史/决策叙事，由验证套件强制。
理由：源码描述当前行为，版本沿革属于 `b-Office`。
需要解释"为什么这样"时写原因本身，不写决策编号。

测试代码与文档不受此限制，可以引用决策编号。

## 已发布说明书在 z，不在 Diana

各项目的唯一权威编辑源是 `b-Office/package/`。集中发布把其中的 Markdown 写入该项目
`z-*/docs/`，并重写 `SHA256SUMS`。跨项目读取只走 `diana.docs.catalog` 与对应
`diana.docs.<域>`，不在 Diana 里保存正文副本，也不手维护文件清单。
