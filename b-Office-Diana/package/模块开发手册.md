# 模块开发手册

面向为 HistoryVulcan 开发模块的人和 AI。Diana 把工作树、候选门禁、调用型试用和正式发布暴露成
MCP 工具；源码编辑、审查以及把验证后的改动带回主树仍由开发者完成。无需记发布脚本路径，
也不需要为了看一眼候选模块而把它发布到正式槽。

**工作区边界：AI 长期只在 Diana 管理的 `F:\ai工作区` 工作。** Janus、Mercury、Minerva 等模块仓库
主线是源码基线、合并目标和正式发布来源，不是 AI 的日常编辑目录。AI 不应直接进入这些主线目录修改；
由 `diana.worktree.create` 从主线拉出分支，所有真实改动、提交和候选验证都发生在 F 盘工作区，最后再由
当前开发会话把分支改动带回对应主线。

本手册只负责**流程**：从开工作区到正式发布，每一步用哪条命令、卡住时看哪里。
**接口事实不在这里**——宿主能注册什么窗口、命令怎么命名、MCP 如何暴露，由 HistoryVulcan
自己的文档作数，读法见下一节。

## 先学会查文档

跨项目读文档只有一条路：**先 `diana.docs.catalog` 拿到通道索引，再调用其中一条通道**。
不要去打开别的项目的 worktree，也不要依赖手写的文件表——两者都会过期。

```
diana.docs.catalog                       # 列出全部通道与各自的文件名，把输出留在对话里
diana.docs.vulcan                        # 只列出宿主通道里有哪些已发布文档
diana.docs.vulcan file=HistoryVulcan_API与指令手册.md
```

各模块的消费文档同理（`diana.docs.janus`、`diana.docs.mercury`、`diana.docs.minerva`、
`diana.docs.diana`……通道名以 catalog 的输出为准）。读到的是各项目**正式 z 快照**里的
已发布 Markdown，不是源码树里正在改的草稿。

开发模块时最常查的几份：

| 想知道 | 去哪查 |
|---|---|
| 宿主提供哪些 API、指令怎么写 | `diana.docs.vulcan file=HistoryVulcan_API与指令手册.md` |
| 能注册什么窗口、页面怎么嵌 | `diana.docs.vulcan file=HistoryVulcan_UI风格与嵌入页面规范.md` |
| 运行时有哪些已知限制 | `diana.docs.vulcan file=HistoryVulcan_运行时约束与已知限制.md` |
| 宿主升级后消费侧要改什么 | `diana.docs.vulcan file=HistoryVulcan_消费变更摘要.md` |
| 别的模块对外暴露了什么 | `diana.docs.<该模块通道>` |
| 本手册自身 | `diana.docs.diana file=模块开发手册.md` |

## 全流程

```
diana.docs.catalog + diana.docs.vulcan   先读正式宿主合同
        ↓
diana.worktree.create   开一个 AI 工作区（新分支，不碰主树）
        ↓
       改代码
        ↓
diana.release.start worktree=<工作区>   从工作区构建候选 + 跑门禁（不促级）
        ↓
diana.trial.load / call / unload    候选装进内存，逐条调用验证
        ↓
  审查改动；以 squash/no-commit 方式带回主树，保持主树未提交
        ↓
diana.release.start publish=true    从主树正式促级到 z + 热重载进宿主
        ↓
       提交源码与 z（同一个提交）
        ↓
diana.worktree.remove   回收工作区（分支保留）
```

## 一、开工作区

```
diana.worktree.create project=2026-021-HistoryMercury slug=explorer-notify agent=claude
```

得到 `F:\ai工作区\<项目>\<短SHA>-<序号>-<标识>`，分支 `ai/<项目>/<同名>`。

同时会在工作区里生成 `Directory.Build.user.props`，把 `HistoryVulcanPackageRoot` 指回来源库根。
各工程按相对路径引用宿主快照，而工作树落在库根之外，少了这个覆盖点会报上百个「找不到类型」。
该文件不入库（各项目 `.gitignore` 已登记），所以工作区从诞生起就是干净的。

- **不要在模块主树上改**。主树是发布和对照的基准；工作区是 AI 的唯一日常编辑面，分支提交可再生但
  主树提交是正式发布来源。
- 位置不硬编码：`diana.worktree.root path=...` 改默认，或单次传 `root=`。默认 `F:\ai工作区`。
- 目录名是 `<短SHA>-<序号>-<开的AI>-<要解决的问题>`，`agent=` 必填：工作区留在盘上的时间
  远长于开它的那轮对话，没有来源和意图就没人敢动它。
- **开销要克制**。项目里已经有一个"开了没干活"的工作区（无提交、无改动）时，默认拒绝再开一个——
  那多半是上一轮对话的残留，接着用或先回收即可；确实要并行才传 `confirm=true`。
  对话窗口随时废弃，工作区不会跟着消失。
- `remove` 在分支有未并回 main 的提交时默认拒绝，确认要丢弃才传 `force=true`。
- `diana.worktree.list` 会逐个报「干净 / 有改动」，收尾前扫一眼别漏下未提交的东西。

**唯一的例外是 Diana 自己。** Diana 是造工作区的工具，没法用自己造的工作区改自己，
所以改 Diana 必须动本仓库主树——这是特例，不要推广到其他模块。

## 二、改代码

模块对宿主的依赖面是**已发布的 z 快照**，不是宿主源码树。

这不是洁癖，是踩过的坑：Mercury 4.5.1 的 csproj 写的是「只要宿主源码树存在就引用源码工程」，
于是宿主工作区一有未发布的在途改动，模块就链接到根本没在运行的宿主二进制，
装载时在 WPF 视图构造处抛 `XamlParseException: 设置 connectionId 时引发了异常`，
宿主只记一行 Warn 继续走，**桌面坞从桌面上无声消失**。

所以新模块的 csproj 应当：

- 默认 `HintPath` 引用 `z-HistoryVulcan/host/HistoryVulcan.*.dll`，`<Private>false</Private>`；
- 要对宿主源码联调时**显式**传 `-p:HistoryVulcanSourceAvailable=true`，不做自动切换；
- 加一个前置校验目标，两条路径各自检查前提缺失时直接报错，而不是报成一堆「找不到类型」。

可用 `b-Code-Samples/` 下的 DemoModule 作为起点（`ModuleInfo`、命令类、`.panel.json`）。

另一条同源的坑：**测试工程不会从模块工程传递 `HintPath` 引用**。模块侧从
`ProjectReference` 改成 `Reference` 之后，Smoke 必须自己声明需要的宿主程序集。

## 三、构建候选并跑门禁

```text
diana.release.start name=HistoryMercury worktree=<工作区名或绝对路径>
diana.release.status                                # 仍在跑 / 成功 / 失败 + 日志末尾
diana.release.log run=<run标识> lines=120           # 要看全量时
```

`worktree=` 可传 `diana.worktree.create` 返回的绝对路径，也可传该项目在 AI 工作区根下的目录名。
发布器会把它转换为底层脚本的 `-SourceWorktree`，并把正式 Vulcan 快照根传给所有子进程。
`worktree` 与 `publish=true` 互斥：工作区只能产出候选并跑门禁，不能直接写正式 z。

管线以**分离子进程**运行，`start` 立刻返回 `run` 标识。状态只落日志文件，
所以即使管线在收尾时热重载了模块（发布 Diana 时会重载 Diana 自己），追踪也不受影响。

`status` 的结构化结果可直接判定，不必解析文本：

```json
{"run":"...","finished":true,"exitCode":0,"success":true,"log":"..."}
```

门禁包括：候选构建、Diana 强制对齐的模块合同、以及登记表里为该模块配置的验证（通常是 Smoke）。
**门禁拦下来时，优先改代码，不要改门禁的期望值**——除非那个期望本身描述的就是过时的事实
（例如新增了一个命令类、模块版本号变了）。这类修正要在提交信息里说明为什么。

## 四、调用型试用

门禁绿了不等于装进宿主就能用。把候选**装进内存**逐条调用：

```
diana.trial.load path=F:\ai工作区\<项目>\<工作区>\z-<模块> ui=true
diana.trial.list
diana.trial.call name=janus.proj.list args="status=true"
diana.trial.unload
```

这条通道刻意不做三件事：不写盘（不改 settings、不动模块槽、不碰正式 z）、
不做发现（只认你给的路径）、不进宿主实注册表（候选命令只能经 `trial.call` 调用，
不与正式模块抢注册，也不出现在补全和 MCP 工具表里）。

代价与边界：

- 默认不创建 UI，验的是调用面；人工验收界面时显式加入 `ui=true`，仍不进入正式发现表或 MCP 工具面。
- `ui=true` 的界面**由 Vulcan 前端创建，不在 Diana 所在的后台进程**。命令从哪儿发都行（控制台、MCP），
  但必须有一个已连接的 Vulcan 前端：前端会另装一份候选程序集建窗口，`diana.trial.unload` 负责让它拆掉。
  前端没连上时 `ui=true` 直接失败，不会悄悄退化成无界面试用。需要宿主 **3.11.4** 及以上
  （更早的宿主没有 `vulcan.module.trialui.*`，会报「未知指令」）。
- 候选的 `Attach` 是它自己的代码，可能启动监视器、全局快捷键一类的**进程级副作用**，
  这些副作用会与正式模块并存，直到 `unload`。
- 由宿主而非模块登记的命令不在试用面里（实测 Janus 宿主侧 40 条、试用面 39 条）。

## 五、正式促级

候选验证完成后先审查差异，再把工作区改动以 **squash/no-commit** 方式带回项目主树，使主树保留
待发布的源码改动但尚未生成“已经发布”的提交。Diana 不提供 commit、merge 或 push 命令；这一步必须
由当前开发会话显式完成并复核 `git status`。不要把工作区路径传给正式促级。

```text
diana.release.start name=HistoryMercury publish=true
diana.release.status run=<返回的run标识>
```

促级是原子的：先备份现有 z，失败自动回滚。正式宿主在运行时**不需要关闭 Vulcan**——
管线原地覆盖快照并调 `vulcan.module.reload` 热重载。

促级前必须对齐三处身份，否则管线直接拒绝：

| 位置 | 内容 |
|---|---|
| 版本源 | csproj 的 `Version` 或 `<模块>Version.props` |
| 源清单 | `b-Code-*/module.manifest.json` |
| 快照清单 | `z-<模块>/module.manifest.json`（由管线写入） |

新模块要能被管线发布，需在 `2026-019-HistoryDiana/b-Code/module-publish.manifest.json`
登记一项，并提供构建脚本。可直接照抄任一现有模块的构建脚本逐词替换——
事务结构（stage/backup/failed + 校验和清单）必须保持一致。
`diana.release.modules` 可查当前已登记的模块。

## 六、先部署后提交

**顺序是先部署、后提交，不能反过来。**

反过来的问题是：提交里写着「已发布」，但发布可能在之后的门禁里失败，仓库于是留下一条
谎报状态的提交；而且源码与 z 分属两次提交，中间存在不一致窗口。

现在的顺序把「部署成功」变成最终提交的前置条件：候选分支可以保留开发提交，但带回主树时不要
先生成最终合并提交；拿到促级结果和校验和之后再回填文档，然后把**源码与 z 放在同一个主树提交里**。
管线跑完会明确提示这一步。提交、推送和 PR 都不是 Diana 发布命令的隐式动作。

工作区里的改动合并回主干后，用 `diana.worktree.remove` 回收；分支一律保留，不删提交。

## 卡住时看哪里

| 现象 | 先看什么 |
|---|---|
| `release.status` 一直「仍在运行」 | `release.log` 看末尾；管线子进程可能已死在某一步 |
| 装载后试用面是空的 | 候选是否链接到了没在运行的宿主（见第二节） |
| 门禁报「模块版本 expected≠actual」 | 三处身份没对齐 |
| 促级后宿主没换新 | 看管线末尾是否成功热重载；未运行时下次启动才装载 |
| 桌面上的 UI 消失但命令还在 | 宿主日志搜「创建 UI 模块 ... 失败」，多半是建界面时抛异常 |

## 相关命令一览

| 命令 | 用途 |
|---|---|
| `diana.worktree.root/create/list/remove` | AI 工作区 |
| `diana.release.modules/start/status/log` | 发布管线 |
| `diana.trial.load/list/call/unload` | 候选调用型试用 |
| `diana.docs.catalog` / `diana.docs.<通道>` | 跨项目已发布说明书；查宿主接口和别的模块都走这里 |

## MCP 暴露边界

Diana 模块声明 `mcpExposure: standard`。当前固定登记 26 条命令，另按现场 `z-*` 动态登记文档通道；
运行时自动生成的命令面当前为 31 条。点号命令投影为下划线工具名，例如
`diana.release.start` → `diana_release_start`。

| MCP 等级 | 命令 |
|---|---|
| `readonly` | `docs`、`kit`、`project` 全部；`relay.list/describe`；`release.modules/status/log`；`trial.list`；`worktree.list` |
| `standard` | `relay.call`；`release.start`；`trial.load/call/unload`；`worktree.root/create/remove` |

`worktree.root` 省略参数时虽然只是查询，但同一描述符也能写设置，因此整体按 `standard` 暴露。
候选模块的私有命令表不直接投影 MCP；`trial.call` 是唯一入口。`relay.call` 只能调用当前 MCP 策略
已经可见的工具，不能越过宿主策略访问 hidden/dangerous 工具。
